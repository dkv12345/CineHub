# CHAPTER 3. SYSTEM ANALYSIS

This chapter establishes the analytical foundation of the CineHub platform. It translates the domain challenges identified in Chapter 1 and the theoretical principles surveyed in Chapter 2 into verifiable system requirements, formal business rules, actor models, use case specifications, Business Process Model and Notation (BPMN) workflows, and balanced Data Flow Diagrams (DFDs). All analytical artefacts in this chapter are aligned with the implemented domain models, database constraints, and service contracts of the CineHub monorepo.

## 3.1. Project Development Process

### 3.1.1. Requirement Collection and Stakeholder Analysis

Requirement collection for CineHub combined comparative analysis of commercial cinema platforms in Vietnam (CJ CGV, Lotte Cinema, Galaxy Cinema, BHD Star, Beta Cinemas, and Moveek), reverse-engineering of public exhibition data feeds, and scenario-based walkthroughs of the end-to-end moviegoing journey. Rather than treating cinema ticketing as a generic CRUD web application, the engineering team analysed the operational tensions among four primary internal perspectives: the moviegoer seeking low-friction discovery and transparent pricing, the box-office and gate staff requiring sub-second ticket verification, the cinema administrator managing schedules and price rules, and the platform reliability engineer preventing race conditions during peak releases.

Each stakeholder group introduced distinct requirement dimensions. Unregistered guests required fast server-side rendered (SSR) catalogue browsing, rich filtering by format (`TWO_D`, `THREE_D`, `IMAX`, `FOUR_DX`, `SCREENX`, `DOLBY`, `LED`), and conversational discovery without mandatory sign-in. Registered customers required secure account linking across local credentials and Google OAuth 2.0, interactive 2D and 3D Point-of-View (POV) auditorium seat selection, deterministic 15-minute seat holds, concession bundling, promotional voucher application, and cryptographic electronic tickets. Operational and administrative stakeholders required role-based access control (RBAC), anti-passback QR check-in scoped to specific cinema venues (`User.cinemaId`), automated catalogue synchronisation from Galaxy Cinema feeds, and financial reconciliation guarantees.

### 3.1.3. System Modeling and Design Workflow

The system modelling workflow followed a top-down, model-driven progression to ensure that no architectural component or database table was introduced without a traceable requirement:

1. **Domain and Stakeholder Scoping**: Context mapping (D01) established the system boundary between CineHub and five external actors (Galaxy Cinema data feed, Google Identity Services, SMTP Mail Server, Payment Gateways, and Google Gemini API).
2. **Functional Decomposition via UML Use Cases**: Six partitioned UML 2.5 use case diagrams (D13a–D13f) captured actor goals and formalised mandatory `<<include>>` dependencies (such as authentication and seat lock acquisition) alongside optional `<<extend>>` behaviours (such as 3D POV preview and voucher application).
3. **Behavioral and Temporal Modeling via BPMN 2.0**: Six BPMN process models (D15–D18) specified swimlane responsibilities, decision gateways, timer boundary events (the 10-minute OTP timer and the 15-minute seat-hold timer), and compensation flows (automated seat release upon timeout or payment failure).
4. **Information Flow Verification via DFD**: Hierarchical Data Flow Diagrams at Level 0 (D19a) and Level 1 (D19b, D20, D21a, D21b) mapped every data transformation between external entities, application processes, and polyglot data stores (MySQL, Redis, and MongoDB), ensuring input–output conservation across levels.
5. **Structural and Contract Formalization**: The analysis models directly drove the 39-model Prisma relational schema, the OpenAPI 3.1 contract generated from shared Zod schemas (`@cinehub/contracts`), and the sequence and state machine models presented in Chapter 4.

### 3.1.4. Implementation and Validation Plan

Implementation was structured around an Nx monorepo (`apps/web`, `apps/core-api`, `apps/aggregator`, `libs/db`, `libs/shared/contracts`, and domain-sliced `libs/web/*` packages) governed by strict module boundary rules and a feature-branch Git workflow. Every requirement identified in this chapter is paired with a validation mechanism:

- **Contract and Schema Validation**: Shared Zod schemas validate all HTTP payloads at the Express middleware boundary and generate typed Angular clients, while 33 SQL `CHECK` constraints and unique lock columns enforce data invariants at the storage engine level.
- **Automated Unit and Integration Verification**: Vitest test suites verify service-layer business rules (authentication token rotation, OTP cooldowns, catalogue filtering, concession calculation, and NLP intent classification).
- **End-to-End and Concurrency Verification**: Playwright browser suites validate user journeys, while concurrent seat-locking scenarios verify that $N$ simultaneous requests for the same seat yield exactly one `201 Created` hold and $N - 1$ `409 Conflict` responses.

### 3.2.1. Guest User

The Guest User (`ACT-01`) represents any unauthenticated visitor accessing CineHub via desktop or mobile browsers. Guests can explore the landing page hero banners (`Promotion`), browse `NOW_SHOWING` and `COMING_SOON` catalogues, inspect full movie details (synopsis, `AgeRating`, `MovieCredit` cast and directors, YouTube trailers, and ratings), and query showtimes across provinces and cinema venues. Guests can also interact with the CineBot AI widget to ask natural-language questions in Vietnamese and view the 2D/3D auditorium seat map for any open showtime. However, when a guest attempts to lock seats, proceed to checkout, or submit a movie review, the Angular `authGuard` and backend `requireAuth` middleware intercept the action and require authentication while preserving the target route for post-login redirection.

### 3.2.2. Registered Customer

The Registered Customer (`ACT-02`) is an authenticated user holding an active account (`UserStatus.ACTIVE`, `UserRole.CUSTOMER`). In addition to inheriting all Guest capabilities, a Registered Customer can acquire temporary 15-minute seat holds (`ShowtimeSeat`), select ticket tiers (`ADULT`, `STUDENT`, `CHILD`, `MEMBER`), add food and beverage combos (`Concession`), apply promotional vouchers (`Voucher`), and execute online payments. After payment confirmation, the customer receives electronic tickets with dynamic HMAC-SHA256 QR codes, views upcoming and past bookings in the _My Tickets_ portal, manages personal profile attributes, links a Google account, bookmarks favourite films (`Favorite`), subscribes to release alerts (`MovieSubscription`), and writes ratings and reviews (`reviews` collection in MongoDB).

### 3.2.3. Administrator

In the operational model of CineHub, internal personnel are divided into two role-scoped actors enforced by `UserRole`:

- **System Administrator (`UserRole.ADMIN`)**: Possesses global administrative privileges across all cinema chains and venues. The administrator curates movie records, configures auditorium layouts, schedules showtimes without room time-slot collisions, defines multidimensional pricing matrices (`PriceRule` by chain, screen format, room tier, seat type, ticket type, and day type), manages voucher campaigns, inspects revenue and occupancy reports, and monitors or manually triggers the Galaxy synchronization pipeline.
- **Cinema Staff (`UserRole.STAFF`)**: Represents gate attendants and box-office clerks assigned to a specific cinema venue via the foreign key `User.cinemaId`. Staff members access the QR scanner interface to validate customer tickets upon entry, verify that the ticket belongs to a showtime at their assigned cinema, transition ticket state from `VALID` to `USED` (anti-passback), and execute manual lookup by booking code or phone number when a customer's screen is damaged.

### 3.2.4. Cinema or Showtime Data Provider

The Cinema or Showtime Data Provider (`ACT-05`) is an external upstream data source—specifically the public mobile and web endpoints of Galaxy Cinema (`CinemaChain.code = 'GALAXY'`). Because cinema exhibition schedules change daily, the `apps/aggregator` worker periodically fetches session feeds, movie detail pages, and cinema lists from this provider, archives raw payloads with SHA-1 content hashes into MongoDB (`crawl_raw_items`), normalises entities through `galaxyAdapter`, and upserts structured records into MySQL (`Province`, `Ward`, `Cinema`, `Auditorium`, `Movie`, `Showtime`). This actor is read-only and untrusted: CineHub sanitises all upstream data, isolates external scores (`MovieSource.sourceScore`) from internal user ratings (`Movie.ratingAvg`), and generates deterministic auditorium seat layouts locally because upstream feeds do not expose seat-level inventory.

### 3.2.5. External Payment Provider

The External Payment Provider (`ACT-06`) encompasses integrated Vietnamese digital payment gateways—VNPay, MoMo, and ZaloPay—together with VietQR bank transfer generation. During checkout, CineHub constructs a signed payment request containing the unique transaction reference (`Payment.txnRef`), order amount in VND, and return URL, then redirects the customer to the gateway. Once the customer authorises payment, the gateway acts as an autonomous actor that sends an asynchronous server-to-server Instant Payment Notification (IPN) webhook to CineHub. CineHub verifies the cryptographic HMAC signature (`HMAC-SHA512` for VNPay, `HMAC-SHA256` for MoMo and ZaloPay) and reconciles the payment amount before committing the booking and issuing tickets.

### 3.2.6. External AI Service

The External AI Service (`ACT-08`) is the Google Gemini API, invoked exclusively by the backend `chatbot` module and the offline embedding job (`embed-movies.js`). It serves two distinct roles: (1) transforming movie metadata and natural-language user queries into 768-dimensional dense vectors via `gemini-embedding-001` for cosine similarity retrieval in MongoDB (`movie_embeddings`), and (2) synthesising conversational Vietnamese responses via generative models (`gemini-2.5-flash`) strictly grounded in the `databaseFacts` payload retrieved from MySQL. To guarantee high availability and prevent vendor lock-in, the system treats the External AI Service as an optional enhancement with a deterministic SQL-based fallback whenever API quotas are exceeded or network timeouts occur.

### 3.4.1. Performance and Response Time

Cinema ticketing workloads exhibit high read-to-write asymmetry punctuated by sharp booking spikes when popular blockbusters open for sale. `NFR-PERF-01` and `NFR-PERF-02` bound API latency by combining multi-tier Redis caching (`cache:movies:*` for 600 seconds, `cache:showtimes:*` for 120 seconds, and `showtime:{id}:seats` for 10 seconds) with composite B-tree indexes in MySQL (`(movieId, localDate, status)` on `showtimes` and `(showtimeId, status)` on `showtime_seats`). On the client side (`NFR-PERF-03`), public discovery pages use Angular SSR with event-replay hydration to deliver fast initial paint, while the computationally intensive Three.js WebGL auditorium renderer is lazy-loaded and executed outside Angular's change-detection zone (`NgZone.runOutsideAngular`).

### 3.4.2. Security and Privacy

Security requirements (`NFR-SEC-01` through `NFR-SEC-04`) follow a defence-in-depth posture across authentication, transport, storage, and third-party integration boundaries. Credentials and tokens are never stored in cleartext; user passwords use salted bcrypt hashes, while refresh tokens, email OTPs, and password reset tokens are persisted as one-way SHA-256 digests. To mitigate Cross-Site Scripting (XSS) and Cross-Site Request Forgery (CSRF), short-lived 15-minute access tokens are held in memory by the Angular `AuthStore`, whereas 7-day refresh tokens are isolated in `HttpOnly`, `SameSite=Strict` cookies scoped to `/api`. Privacy is further enforced in the AI subsystem by redacting email addresses, phone numbers, and API keys before persisting chat transcripts to MongoDB (`ai_chat_sessions`), and by anonymising personal data (`deleted+{id}@cinehub.invalid`) upon account deletion.

### 3.4.3. Reliability and Data Consistency

Financial and inventory consistency (`NFR-REL-01` through `NFR-REL-04`) is the primary architectural driver of CineHub. The platform guarantees zero double-booking through four concentric locking layers: atomic Redis Lua scripts, pessimistic `SELECT ... FOR UPDATE` row locks acquired in ascending `seatId` order, optimistic `version` increments on `ShowtimeSeat` and `Booking`, and the nullable unique column `BookingSeat.activeLock`. Similarly, payment processing guarantees exactly-once state transition via the `PaymentWebhookEvent` unique index `(provider, eventKey)` and the nullable unique column `Payment.successLock`. Asynchronous side effects—such as sending ticket emails or synchronising review averages—are protected against message loss and duplication by the Transactional Outbox (`OutboxEvent`) and Idempotent Consumer (`InboxEvent`) pattern.

### 3.4.4. Scalability and Maintainability

Although deployed as a modular monolith to minimise operational overhead, CineHub is structured for horizontal scalability and long-term maintainability (`NFR-MAINT-01`). All primary keys use time-ordered UUID v7 (`CHAR(36) COLLATE ascii_bin`) rather than sequential integers, preventing primary-key contention and enabling cursor-based pagination without `OFFSET` degradation. The `CinemaChain` abstraction decouples catalogue and pricing logic from any single cinema operator, allowing additional chains (such as CGV or Lotte) to be onboarded solely by writing a new ingestion adapter in `apps/aggregator`. Within the Nx workspace, ESLint rules statically block illegal cross-domain imports, and the CI pipeline fails any pull request whose generated OpenAPI specification or Angular client drifts from the canonical Zod schemas in `libs/shared/contracts`.

### 3.4.5. Usability and Accessibility

Usability requirements (`NFR-USAB-01`) focus on reducing cognitive load during time-constrained booking sessions. The interface uses a high-contrast cinema design system, Vietnamese localisation (`@jsverse/transloco`), persistent booking summary drawers, and an unmistakable `MM:SS` countdown badge. To prevent user errors before server round-trips, interactive seat maps immediately disable sold seats, highlight seat zones (`STANDARD`, `VIP`, `SWEETBOX`), and display toast feedback if a customer exceeds the six-seat limit or violates the single-seat gap rule. Accessibility is enforced through semantic HTML landmarks, keyboard focus management via Angular CDK, `aria-label` descriptions on every seat button (including row, number, zone, and status), and automated WCAG 2.1 AA checks in Playwright.

### 3.4.6. Compatibility and Deployment Requirements

`NFR-COMP-01` specifies that the entire platform must be reproducible with a single command (`npm run infra:up && npm run dev`) across standard developer and CI environments. The runtime stack targets Node.js 20+ ESM, Angular 20+, MySQL 8.4 (requiring MySQL $\ge 8.0.16$ for active `CHECK` constraint enforcement), Redis 7 (configured with `noeviction` and Append-Only File persistence for locks and queues), and MongoDB 7. Environment configuration is validated at startup by a strict Zod schema (`apps/core-api/src/platform/config/env.js`) so that missing secrets or malformed connection strings fail fast before the HTTP server binds to a port.

## 3.5. Business Rules and System Constraints

Business rules (`BR-01` through `BR-24`) define the domain invariants that govern CineHub independent of any specific user interface. In the CineHub architecture, these rules are enforced across three complementary layers: shared Zod schemas (`@cinehub/contracts`), domain service logic (`apps/core-api/src/modules/*`), and relational constraints in `libs/db/prisma/schema.prisma` and `migration.sql`.

### 3.5.1. Movie and Showtime Validity Rules

Movie and showtime rules govern how catalogue items are classified, scheduled, priced, and synchronised from external feeds:

- **BR-01 (Age Rating Classification and Enforcement)**: Every movie must carry a valid Vietnamese cinema classification from `AgeRating` (`P` for all audiences, `K` for under 13 with guardian, `T13`, `T16`, `T18`, or `C` prohibited). movies with status `C` or soft-deleted (`deletedAt IS NOT NULL`) are never exposed to public discovery or booking endpoints.
- **BR-02 (Showtime Temporal Integrity)**: For every showtime, `endTime` must be strictly greater than `startTime` (enforced by SQL constraint `chk_showtime_time`: `endTime > startTime`), and `durationMin` on a movie, when present, must be positive (`chk_movie_duration`).
- **BR-03 (Auditorium Non-Overlap Rule)**: Two active showtimes (`status != 'CANCELLED'`) assigned to the same `Auditorium` must not overlap in time, including a mandatory turnaround buffer for cleaning between screenings. This rule is enforced within a serialised transaction locking the parent `Auditorium` row during schedule creation.
- **BR-04 (Showtime Bookability Window)**: Customers may only acquire seat holds or create bookings for showtimes whose status is `OPEN` (or active `SCHEDULED` within the booking window) and whose `startTime` is in the future. Showtimes in `SOLD_OUT`, `CANCELLED`, or `FINISHED` state reject all reservation requests.
- **BR-05 (Multi-Dimensional Price Resolution)**: Every bookable showtime must have non-negative integer VND prices (`chk_price`: `price >= 0`) in `ShowtimePrice` for each `(seatTypeId, ticketTypeId)` pair. When upstream crawled data does not include pricing, the system resolves prices deterministically from `PriceRule` matching `(chainId, format, roomTier, seatTypeId, ticketTypeId, dayType)` with `PriceSource.DEFAULT`.
- **BR-06 (Orphaned Showtime Protection During Crawl)**: If a previously synchronised showtime disappears from the upstream Galaxy feed, the ETL upsert logic checks whether any `Booking` references that showtime: if zero bookings exist, the showtime transitions to `CANCELLED`; if one or more bookings exist, the showtime is preserved and flagged for administrative review rather than deleted or overwritten.

### 3.5.2. Seat Availability and Reservation Rules

Seat reservation rules protect auditorium inventory and optimise seating utilisation:

- **BR-07 (Maximum Seats Per Booking)**: A customer may select and hold at most **6 seats** in a single booking transaction (`MAX_SEATS_PER_BOOKING = 6`, enforced by both the Angular `BookingStore.toggleSeat` method and the backend `holdSeatsRequestSchema` Zod validator). Note that a `SWEETBOX` couple seat (`colSpan = 2`) is modelled as one `Seat` record with a double-width span and pair price.
- **BR-08 (No Single-Seat Gap / Anti-Orphan Rule)**: When selecting seats in a row, a customer must not leave an isolated single `AVAILABLE` seat (`colNumber` gap of 1) trapped between the newly selected seats and an existing `SOLD`, `HELD`, `BLOCKED` seat, or the end of the row/aisle, unless no contiguous alternative exists in that row.
- **BR-09 (All-or-Nothing Multi-Seat Lease)**: If a customer requests a hold on $k$ seats ($1 \le k \le 6$), either all $k$ seats are free in Redis and `AVAILABLE` in MySQL and are locked together as a single atomic unit, or zero seats are locked and the request fails with HTTP `409 Conflict` (`SEAT_TAKEN`).
- **BR-10 (Exclusive Active Seat Lock Invariant)**: At any point in time, a `ShowtimeSeat` may be associated with at most one active (non-expired, non-cancelled) `BookingSeat`. This rule is guaranteed at the database level by the nullable unique column `BookingSeat.activeLock` (`CHAR(36) UNIQUE`) combined with `chk_active_lock` (`activeLock IS NULL OR activeLock = showtimeSeatId`): active holds/bookings set `activeLock = showtimeSeatId`, whereas expired or cancelled bookings set `activeLock = NULL`.

### 3.5.3. Seat-Hold Expiration Rules

Temporary holds are strictly time-bounded to prevent inventory hoarding:

- **BR-11 (Unified 15-Minute Hold TTL)**: Every seat hold has a fixed lifetime of **900 seconds (15 minutes)** defined by the shared constant `SEAT_HOLD_SECONDS = 900` in `@cinehub/contracts`. Both `ShowtimeSeat.heldUntil` and `Booking.expiresAt` are set to `NOW() + 900s`, and the Redis key `seat:{showtimeId}:{seatId}` is created with `EX 900`.
- **BR-12 (Owner-Checked Lease Release)**: A Redis seat lease may only be deleted before its natural TTL by the user or booking session that created it, verified atomically via the Lua compare-and-delete script (`RELEASE_SEAT_LEASES_LUA`) comparing the key's value prefix against `userId`.
- **BR-13 (Compensating Release on Expiration)**: When a `PENDING` booking reaches `expiresAt` without confirmed payment (detected either by the delayed `booking-expiry` job or the 60-second reconciliation cron), the system executes a single compensating transaction that transitions `Booking.status` to `EXPIRED`, clears `BookingSeat.activeLock = NULL`, resets `ShowtimeSeat.status` to `AVAILABLE` (with `heldByBookingId = NULL`, `heldUntil = NULL`, and incremented `version`), cancels any `INITIATED` `Payment`, and releases any `RESERVED` `VoucherRedemption` while decrementing `Voucher.usedCount`.

### 3.5.4. Order and Payment State Transitions

Financial calculations, voucher redemptions, and payment state transitions obey strict deterministic invariants:

- **BR-14 (Server-Side Monetary Invariant)**: All monetary values are stored as non-negative integer VND (`Int`). The booking total must always satisfy `totalAmount = subtotalAmount + serviceFee - discountAmount` with `totalAmount >= 0`, where `subtotalAmount` is the sum of `BookingSeat.price` snapshots plus `BookingConcession.totalPrice` (`quantity * unitPrice`, with `1 <= quantity <= 20` per `chk_bc_qty`). This invariant is enforced both in the service layer and by the SQL constraint `chk_booking_amount`.
- **BR-15 (Voucher Redemption Quota and Reservation)**: A voucher (`Voucher`) is applicable only if `isActive = true`, `NOW() BETWEEN startAt AND endAt`, `subtotalAmount >= minOrderAmount`, `usedCount < usageLimit`, and the customer has fewer than `perUserLimit` non-released redemptions. Applying a voucher atomically increments `usedCount` (`WHERE usedCount < usageLimit`) and creates a `VoucherRedemption` with status `RESERVED`; payment confirmation transitions it to `REDEEMED`, whereas booking cancellation or expiration transitions it to `RELEASED` and restores the quota.
- **BR-16 (Authoritative Server-to-Server Payment Confirmation)**: Browser return URLs (`/checkout?resultCode=0`, `vnp_ResponseCode=00`, or `status=1`) are used solely to render UI feedback and poll order status. A `Booking` transitions from `PENDING` to `CONFIRMED` only when an authenticated gateway IPN/webhook (or verified server-side gateway query) confirms that the exact `Booking.totalAmount` was paid.
- **BR-17 (Single Successful Payment Per Booking)**: A booking may have multiple `Payment` attempts (`INITIATED` $\to$ `FAILED` or `CANCELLED`), but at most one `Payment` may reach `SUCCESS` (or `REFUNDED`). This is enforced by the nullable unique column `Payment.successLock` (`CHAR(36) UNIQUE`) and SQL constraint `chk_payment_success_lock`, which requires `successLock = bookingId` when `status IN ('SUCCESS', 'REFUNDED')` and `successLock IS NULL` otherwise.
- **BR-18 (Late Payment Refund Rule)**: If a valid `SUCCESS` payment webhook arrives after a booking has already transitioned to `EXPIRED` and its seats have been released or sold to another customer, the system records the `Payment` as `SUCCESS` for audit accuracy, leaves the booking as `EXPIRED`, and automatically creates a `Refund` record (`RefundStatus.REQUESTED`, `amount = payment.amount`) for financial restitution.

### 3.5.5. Ticket Issuance and Cancellation Rules

Electronic tickets and gate check-in operations follow strict cryptographic and anti-passback constraints:

- **BR-19 (One-to-One Seat-to-Ticket Mapping and Stateless HMAC QR)**: Tickets (`Ticket`) are generated exclusively inside the payment-confirmation transaction, with a strict 1:1 relationship between `BookingSeat` and `Ticket` (`bookingSeatId UNIQUE`). The system never stores raw QR tokens in the database; instead, the QR string is computed dynamically as `ticketId + "." + HMAC_SHA256(QR_HMAC_SECRET, ticketId + ":" + qrVersion).slice(0, 16)`. Incrementing `Ticket.qrVersion` immediately invalidates any previously screenshotted QR image.
- **BR-20 (Venue-Scoped Single-Use Check-in / Anti-Passback)**: A ticket can be checked in only by a user with `UserRole.STAFF` (or `ADMIN`) whose assigned `User.cinemaId` matches the `Showtime.cinemaId` of the ticket's booking, and only when `Ticket.status == 'VALID'` on the scheduled screening date. Check-in atomically updates `Ticket.status` to `USED`, sets `usedAt = NOW()`, and records `checkedInById`. Any subsequent scan of a `USED` or `VOID` ticket is rejected with an audible/visual alert displaying the original check-in timestamp.
- **BR-21 (Ticket Voiding on Refund)**: Confirming a full or partial refund transitions the associated `Ticket.status` from `VALID` to `VOID`, preventing gate entry, and transitions `Booking.status` to `REFUNDED` or `PARTIALLY_REFUNDED`.

### 3.5.6. Administrative Permissions and Data Integrity

Role permissions, credential constraints, and referential integrity rules protect the platform against unauthorised mutations and data corruption:

- **BR-22 (Role-Based Access Control Hierarchy)**: Every protected endpoint validates both authentication (`requireAuth`) and role membership (`requireRole`). `CUSTOMER` users may access only their own bookings, tickets, and profile; `STAFF` users may access check-in endpoints only for their assigned `cinemaId`; `ADMIN` users have full CRUD access to catalogue, scheduling, pricing, voucher, and operational endpoints.
- **BR-23 (Dual-Provider Credential Invariant)**: Every `User` record must have at least one valid authentication mechanism (`passwordHash IS NOT NULL OR googleId IS NOT NULL`, enforced by SQL constraint `chk_user_credential`). Accounts with `UserStatus.LOCKED` or `DELETED` are rejected at login and token refresh.
- **BR-24 (Financial Referential Integrity and Soft Deletion)**: All foreign keys on financial and inventory tables (`Booking`, `BookingSeat`, `Ticket`, `Payment`, `Refund`, `ShowtimeSeat`) use `ON DELETE RESTRICT` and `ON UPDATE RESTRICT` so that historical transactions can never be orphaned or silently cascaded. Deletions of `User` and `Movie` records are performed exclusively via soft deletion (`deletedAt`), with deleted user emails anonymised to preserve audit trails while freeing the email address for future registration.

## 3.7. Business Process Modeling (BPMN)

Whereas use cases specify _what_ goals actors achieve, Business Process Model and Notation (BPMN 2.0) diagrams specify _how_ those goals unfold across organisational swimlanes, decision gateways, timer events, and compensating actions. Six BPMN models (D15 through D18) capture the operational processes of CineHub.

### 3.7.1. User Registration and Authentication Process

The registration and authentication BPMN model orchestrates account creation, 10-minute email OTP verification, local credential login, Google OAuth 2.0 federation, and password recovery across three swimlanes: _Customer / Guest_, _CineHub System (Web + Core API)_, and _External Identity & Mail Providers (Google OAuth / SMTP)_. Figure 3.7.1-1 presents this process.

> **[INSERT FIGURE 3.7.1-1 | D15 | BPMN diagram: user registration, 10-minute OTP, local/Google login, password reset | owner: Kim Ngân | file: 3.7.1.drawio]**
> _Figure 3.7.1-1. BPMN 2.0 process model for user registration, 10-minute OTP verification, local/Google authentication, and password recovery (D15)._

The process begins at the _Start Event_ when a guest opens the authentication view. An exclusive gateway splits the flow into three branches:

1. **Registration and 10-Minute OTP Branch**: The guest submits registration details. The system validates the payload, checks email uniqueness, hashes the password with `bcryptjs` (cost 10), creates an unverified `User` row, stores a SHA-256 salted 6-digit OTP in `email_verification_tokens`, and dispatches the OTP via the _SMTP lane_. An interrupting **10-minute Timer Boundary Event** (`OTP_TTL_MINUTES = 10`) is attached to the _Await OTP Input_ task. If the user submits the valid code before expiry, `emailVerifiedAt` is set, a welcome email is triggered, and the flow merges into session issuance. If the 10-minute timer fires, the token is invalidated and the user must trigger _Resend OTP_ (subject to a 60-second cooldown gateway).
2. **Local and Google Login Branch**: For local login, the system verifies the password hash and checks account status (`ACTIVE` and verified). For Google OAuth, control crosses into the _Google Identity lane_ to validate the `id_token` and either links an existing verified email or provisions a new `GOOGLE` user. Both paths converge at _Issue Dual JWT Session_ (15-minute access token + 7-day `HttpOnly` refresh token in a new `familyId`), terminating at the _Authenticated Session End Event_.
3. **Password Recovery Branch**: Submitting a forgot-password request generates a 15-minute reset token (`RESET_TOKEN_TTL_MS`), emails the reset link via SMTP, validates the token on return, updates `passwordHash`, and revokes all active refresh token families before ending.

The discovery BPMN model traces how a user navigates from initial landing or natural-language search to selecting a concrete showtime and entering the seat map. Figure 3.7.2-1 depicts this process.

> **[INSERT FIGURE 3.7.2-1 | D16 | BPMN diagram: movie discovery, filtering, and showtime selection with authentication gateway | owner: Kim Ngân | file: 3.7.2.drawio]**
> _Figure 3.7.2-1. BPMN 2.0 process model for movie discovery, multi-criteria filtering, and showtime selection (D16)._

Starting from the _User Visits Platform_ event, the user may browse the SSR homepage catalogue, use the instant debounced search bar, apply multi-criteria filters (genre, format, age rating), or ask CineBot for recommendations. Upon selecting a movie or cinema, the system queries Redis cache (`cache:showtimes:*`) and MySQL (`Showtime`, `ShowtimePrice`) for active screenings on the chosen `localDate` (`Asia/Ho_Chi_Minh`). If no sessions exist on the requested date, a fallback gateway automatically selects the nearest available screening date so the user never encounters a dead-end empty screen. When the user clicks a specific showtime pill, an exclusive decision gateway evaluates **"Is User Authenticated?"**: if authenticated, the user proceeds directly to the seat reservation process; if unauthenticated, the system captures the target `/seats/:showtimeId` URL, routes through the authentication subprocess (Section 3.7.1), and resumes seamlessly at the chosen showtime.

### 3.7.3. Seat Selection and Temporary Reservation Process

The seat selection BPMN model (Part A of D17) specifies the fine-grained interaction between the customer, the Angular `BookingStore`, the Redis lease engine, and MySQL row locking. Figure 3.7.3-1 illustrates this workflow.

> **[INSERT FIGURE 3.7.3-1 | D17a | BPMN diagram: seat selection and 15-minute temporary reservation | owner: Kim Ngân | file: 3.7.3 – 3.7.5.drawio]**

The process starts when the customer loads the auditorium seat map (`ShowtimeSeat`). As the customer toggles seats (optionally launching the 3D WebGL POV preview subprocess), an exclusive gateway checks two business rules on each selection: `selectedSeats <= 6` (`BR-07`) and _No Single-Seat Gap_ (`BR-08`). Violations trigger an immediate inline warning and loop back to seat selection. When the customer confirms the selection, the _Core API lane_ executes the atomic Lua script (`ACQUIRE_SEAT_LEASES_LUA`) in Redis (`SET NX EX 900`). A gateway evaluates the lease outcome: if any seat is already leased, the process takes the exception path, returning HTTP `409 Conflict`, refreshing the seat map, and prompting the customer to pick alternative seats. If the Redis lease succeeds, the backend executes a MySQL transaction (`SELECT ... FOR UPDATE`), sets `ShowtimeSeat.status = 'HELD'`, creates the `PENDING` `Booking` and `BookingSeat` rows (`activeLock = showtimeSeatId`), and attaches an interrupting **15-Minute Timer Boundary Event** (`SEAT_HOLD_SECONDS = 900`) that governs the remainder of the checkout lifecycle.

### 3.7.4. Booking, Payment and Ticket Issuance Process

Part B of D17 models the happy-path progression from an active seat hold through concession selection, voucher application, external gateway payment, and cryptographic ticket issuance across three lanes: _Customer_, _CineHub Core API & Worker_, and _External Payment Gateway & SMTP_. Figure 3.7.4-1 shows this process.

> **[INSERT FIGURE 3.7.4-1 | D17b | BPMN diagram: booking, payment, IPN verification, and ticket issuance | owner: Kim Ngân | file: 3.7.3 – 3.7.5.drawio]**
> _Figure 3.7.4-1. BPMN 2.0 process model for concession bundling, voucher redemption, gateway payment, and electronic ticket issuance (D17b)._

With the 15-minute hold timer active, the customer optionally adds concession combos (`BookingConcession`) and optionally enters a voucher code. If a voucher is entered, a gateway checks eligibility and atomically reserves a redemption slot (`VoucherRedemption.status = 'RESERVED'`). The system then computes the authoritative server-side `totalAmount`, creates a `Payment` (`INITIATED`) record, and redirects the customer to the _Payment Gateway lane_ (VNPay, MoMo, or ZaloPay). Upon payment authorisation, two parallel paths occur: the browser redirects back to CineHub's result screen (display-only), while the gateway sends a signed IPN webhook to the _Core API lane_. An exclusive gateway verifies the HMAC signature, checks idempotency (`PaymentWebhookEvent`), and confirms `Booking.status == 'PENDING'`. Upon verification, an ACID transaction marks `Payment` as `SUCCESS` (`successLock = bookingId`), transitions `Booking` to `CONFIRMED` and `ShowtimeSeat` to `SOLD`, marks `VoucherRedemption` as `REDEEMED`, generates HMAC-signed `Ticket` records (`VALID`), deletes the Redis hold keys, and triggers the outbox worker to email the QR tickets before reaching the _Booking Completed End Event_.

### 3.7.5. Booking Expiration and Failed Payment Process

Part C of D17 models the exception, timeout, and compensation workflows when the 15-minute boundary timer fires, when a payment fails at the gateway, or when a late IPN arrives after expiry. Figure 3.7.5-1 presents this compensation process.

> **[INSERT FIGURE 3.7.5-1 | D17c | BPMN diagram: 15-minute timer expiry, failed payment, and seat-release compensation | owner: Kim Ngân | file: 3.7.3 – 3.7.5.drawio]**
> _Figure 3.7.5-1. BPMN 2.0 process model for booking expiration, failed payment handling, seat-release compensation, and late-payment refund (D17c)._

Three trigger events enter this process: (1) the **15-Minute Boundary Timer** (`booking-expiry` delayed job or 60-second reconciliation cron) fires while `Booking.status == 'PENDING'`, (2) the customer explicitly cancels the checkout, or (3) the payment gateway returns a terminal failure webhook (`PaymentFailed`). When a payment failure occurs _before_ the 15-minute timer expires, a decision gateway allows the customer to retry payment with another method while preserving the seat hold. However, once the 15-minute timer expires (or the customer aborts), the **Compensation Subprocess (`releaseSeats`)** executes atomically: `Booking.status` becomes `EXPIRED` (or `CANCELLED`), `BookingSeat.activeLock` is cleared to `NULL`, `ShowtimeSeat.status` returns to `AVAILABLE`, Redis lease keys are deleted via Lua, `Payment` is marked `CANCELLED`, and any `RESERVED` voucher is set to `RELEASED` with `Voucher.usedCount` decremented. Finally, a dedicated gateway handles the race condition where a valid `SUCCESS` IPN arrives _after_ the booking was already marked `EXPIRED`: the system records the payment, creates a `Refund` (`REQUESTED`) task, and notifies the customer, ensuring zero financial discrepancy.

In the manual administrative flow (_Admin lane_ $\to$ _Core lane_), the administrator submits movie, showtime, or `PriceRule` updates. The Core API verifies `requireRole('ADMIN')`, validates the payload with Zod, checks auditorium schedule non-overlap (`FOR UPDATE` on `Auditorium`), writes the changes and materialised `ShowtimeSeat` rows inside a MySQL transaction, and invalidates affected Redis cache keys (`cache:movies:*`, `cache:showtimes:*`). In the automated or admin-triggered synchronisation flow (_Aggregator lane_ $\leftrightarrow$ _Galaxy Source lane_), the worker acquires the distributed lock `crawl:lock:GALAXY` (TTL 3600s), logs a `crawl_runs` entry, performs the cookie handshake, fetches session and movie feeds from Galaxy, archives changed raw payloads into MongoDB (`crawl_raw_items`) by comparing SHA-1 `contentHash`, transforms records via `galaxyAdapter`, and invokes the Core catalog upsert pipeline. The Core pipeline upserts geographic, venue, movie, and showtime records in foreign-key order, resolves default prices from `PriceRule`, protects any disappeared showtime that already has a `Booking` (`BR-06`), seeds deterministic `ShowtimeSeat` availability for the next 7 days, triggers `embed-movies.js` for new films, and flushes Redis caches before completing.

## 3.9. Chapter Summary

This chapter presented the complete system analysis of the CineHub platform. Starting from stakeholder analysis and a 40-story User Story Map (D12) prioritised with MoSCoW, the chapter identified four human actors (`Guest`, `Customer`, `Cinema Staff`, `System Admin`) and four external system actors (`Galaxy Cinema Data Provider`, `External Payment Providers`, `Google Identity & SMTP Services`, and `Google Gemini AI`). It specified 40 traceable Functional Requirements across nine domain modules (`FR-AUTH`, `FR-CAT`, `FR-SHOW`, `FR-SEAT`, `FR-BOOK`, `FR-PAY`, `FR-TKT`, `FR-ADM`, and `FR-AI`), 14 quantitative Non-Functional Requirements (`NFR-PERF`, `NFR-SEC`, `NFR-REL`, `NFR-MAINT`, `NFR-USAB`, and `NFR-COMP`), and 24 formal Business Rules (`BR-01` to `BR-24`) governing showtime validity, 6-seat limits, single-seat gap prevention, 900-second atomic leases, server-side VND pricing invariants, IPN webhook authority, stateless HMAC-SHA256 QR tickets, and venue-scoped anti-passback check-in.

These requirements and rules were then formalised through three complementary modelling paradigms: six UML 2.5 Use Case diagrams (D13a–D13f) accompanied by five detailed use case specifications (D14), six BPMN 2.0 business process diagrams (D15–D18) capturing swimlanes, 10-minute and 15-minute timer boundary events, and seat-release compensation flows, and five balanced Level 0 and Level 1 Data Flow Diagrams (D19–D21) mapped across 12 polyglot data stores (`D1`–`D12`). Chapter 4 builds directly on this analytical specification to define the system architecture, API contracts, physical database schema, sequence interactions, and concurrency state machines.
